**✅ Chapter 13 체크포인트**

1. ML 테스트가 "다크 소울"이라 불리는 이유를 전통 소프트웨어와 비교하여 3가지 관점에서 설명할 수 있으신가요?
    1. 예측 불가능한 확률적 특성 : 같은 입력에 같은 출력이 나오는 일반 소프트웨어와 달리, ML은 부동 소수점 오차나 데이터 분포에 따라 결과가 미세하게 달라진다.
    2. 불투명한 디버깅 환경 : 일반 코드는 디버거로 모든 변수와 로직 상태를 추적할 수 있지만, 딥러닝 모델 내부는 수많은 파라미터가 얽혀 있어 원인 파악이 매우 어렵다. 
    3. 0이 아닌 손실(Loss): “테스트 통과 = 정답” 인 일반 프로그램과 달리, ML 모델은 항상 어느 정도 오차(손실)을 안고 있어 “얼마나 허용 범위 안에 드는가”를 통계적으로 검증해야 한다. 
2. 테스트 수트를 "분류기"로 보았을 때, 오탐(False Alarm)이 왜 위험한지 실제 사례를 들어 설명할 수 있으신가요?
    1. 테스트 수트를 분류기로 보았을 때, 기준은 다음과 같다. 
        1. 실제 상태(Ground Truth): 코드에 진짜 버그가 있는가?
        2. 분류기 판단(Test Result) : 테스트가 실패(버그 감지, detection)했는가 통과(정상)했는가?
        3. 오탐(False Alarms): 정상적인 코드인데 테스트가 실패한는 상황. 
    2. 오탐이 위험한 이유 
        1. 개발 생산성 저하 및 피로도 증가 : 정상적인 기능 추가나 리팩토링임에도 불구하고 사소하거나 잘못 짜인 테스트가 계속 실패하면, 개발자는 진짜 버그를 잡는 대신 테스트 통과용 땜질에 시간을 낭비하게 된다.
        2. 양치기 효과(Alert Fatigue): 테스트 실패 경보가 너무 자주 울리면 개발자들은 “또 그 이상한 테스트가 깨졌겠지”라고 실패를 가볍게 넘기거나, 테스트 코드의 단언문(assert) 자체를 느슨하게 수정하거나 주석 처리해 버린다. 이로 인해 정작 진짜 치명적인 버그가 발생했을 때 이를 놓이게 된다. 
    3. 실제 사례 
        1. 송금 처리 속도 데스트를 위해 “송금 완료 응답 시간은 무조건 100ms 이내여야 한다”라는 비결정론적 타이밍 테스트를 작성하였다고 가정한다. CI 서버의 일시적인 CPU 부하로 인해 코드는 멀쩡한데 105ms가 걸려 테스트가 빈번하게 실패하는 오탐이 발생할 수 있다. 매번 빌드가 멈추는 것에 지친 개발자가 성능/검증 테스트 조건을 마구잡이로 늘려놓거나 검증 단계를 생략할 경우, 이후 진짜 교착 상태(Deadlock)이 발생해 송금 처리가 멈추는 코드가 들어왔을 때 이를 걸러낼 수 없게 된다. 
3. 암기 테스트(`overfit_batches=1`)가 실패했을 때 의심해야 할 원인 5가지를 나열하고, 각각의 디버깅 방법을 떠올릴 수 있으신가요?
    1. 그래디언트 계산 오류 : 특정 레이어의 연산 그래프가 끊겼거나 파라미터가 고정됨.
        1. 디버깅 : 모델 파라미터의 `.requires_grad` 가 `True` 인지 확인. `loss.backward()` 이후 각 레이어의 `param.grad` 가 `None` 이 아니며 정상적으로 갱신되는지 추적 
    2. 데이터 셔플링 오류 : DataLoader에서 입력($x$)과 타깃($y$)의 인덱스 순서가 어긋나 무의미한 데이터를 학습
        1. 디버깅 : 단일 배치를 직접 꺼내서 `(next(iter(dataloader))` $x$ 데이터와 정답 라벨 $y$가 실제로 1:1 매칭되는지 눈으로 출력해 검증 
    3. 전처리 버그 : 정규화 수식 오류(평균을 빼야 하는데 더함 등) 또는 역변환 누락으로 입력 텐서 분포가 깨짐 
        1. 디버깅 : 모델 입력 직전 텐서의 최소/최대/평균(min/max/mean) 및 시각화 결과를 확인하여 의도한 스케일 범위에 있는지 점검
    4. 수치적 문제 : 그래디언트 폭주/소실로 인해 손실값이나 가중치가 발산함
        1. 디버깅 : `gradient_clip_val` 을 설정하여 그래디언트는 클래핑하고, W&B나 로거로 Gradient Norm을 모니터링하거나 FP16 대신에 FP32/BF16으로 정밀도를 전환하여 테스트 
    5. 옵티마이저 수정 오류 : 학습률(lr)이 0이거나 너무 작음, 또는 옵티마이저에 모델 파라미터 전체가 전달되지 않음
        1. 디버깅 : 암기 테스트용으로 학습률을 평소보다 10배 이상 높여보고(예: `lr=1e-3`), `optimizer.param_groups` 에 등록된 파라미터 수와 `model.parameters()` 의 수가 일치하는지 확인 
4. 데이터 기댓값 테스트에서 "느슨한 경계" 원칙이 왜 중요한지, 경계를 너무 엄격하게 잡으면 어떤 문제가 발생하는지 설명해 보세요.
    1. 기댓값 테스트(스모크 테스트)의 목적은 시스템에 '불이 났는지(치명적 오염)' 확인하는 최소한의 방어선이기 때문이다. 사소한 이상치로 인한 불필요한 알람을 줄이고, 단위 변환 오류나 음수 입력 같은 진짜 치명적인 데이터 오염만 안정적으로 포착하기 위해 느슨한 경계가 필수적이다.
    2. 너무 엄격하게 잡았을 때 발생하는 문제:
    - 정상 데이터에 대한 오탐(False Alarm): 예를 들어 사람의 키 범위를 140~190cm로 너무 좁게 잡으면, 130cm 이하(어린이 등)나 195cm 같은 정상 데이터가 유입되어도 테스트가 깨진다.
    - 파이프라인 중단 및 피로도 유발: 유효한 데이터임에도 학습 파이프라인과 자동 배포가 멈추게 된다.
    - 검증 무력화: 잦은 실패에 지친 엔지니어가 검증 조건을 임의로 해제하거나 건너뛰게 되어, 정작 피트(feet) 단위 혼용이나 음수(-10) 같은 진짜 오염 데이터를 잡지 못하는 역효과를 낳는다.
5. 행동 테스트의 "불변성 테스트"와 "방향성 테스트"의 차이를 자신의 프로젝트에 적용하여 각각 1개씩 예시를 만들어 보실 수 있나요?
    1. 불변성 테스트 : 의미에 영향을 주지 않는 변화(노이즈, 반전 등)를 주었을 때 출력 결과가 바뀌지 않아야 함. 
    예시 : 체육시설 안전점검 이미지에 좌우 반전(Horizontal Flip)이나 미세한 밝기 변화(±5%)를 주어도, 위험도 분류 결과(예: '정상' 또는 '위험')나 신뢰도가 유지되어야 함.
    2. 방향성 테스트 : 특정 의미가 강화되거나 약화되는 변화를 주었을 때 ****출력값(확률, 위험도 점수 등)이 예상한 방향(단조 증가/감소)으로 변해야 함.
    예시 : 기존 외벽 균열 이미지에 인위적으로 균열의 길이를 더 늘리거나 크랙을 추가(합성)했을 때, 모델이 출력하는 '위험도 점수(Danger Score)' 또는 '점검 필요 확률'이 기존보다 상승(증가)해야 함.

**✅ Chapter 14 체크포인트**

1. "Make it Run → Make it Fast → Make it Right" 순서에서, 왜 ML에서는 "Fast"가 "Right"보다 먼저 와야 하는지 설명할 수 있으신가요?
    1. 정답이 확실한 일반적인 프로그램과 달리 ML 모델은 항상 어느정도는 틀려있는 확률적인 모델이다. 따라서 “Right”하게 만드는 것에는 끝이 없다. 성능을 개선하기 위해 수많은 실험을 수행하기 위해서는 시험 주기를 단축하는 “Fast”가 먼저 와야 한다. 
2. OOM 오류를 해결하는 4단계 전략을 순서대로 말할 수 있으신가요? Adam이 파라미터의 3~4배 메모리를 쓰는 이유는 무엇인가요?
    1. OOM 오류 해결 4단계 
        1. 1단계 정밀도 낮추기 : `precision="16-mixed"` 로 메모리를 절반으로 줄이고 속도도 빠르게 만듦
        2. 2단계 배치 사이즈 줄이기 : 너무 작아질 경우 학습이 불안정 할 수 있음 
        3. 3단계 그래디언트 축적 : `accumulate_grad_batches = 4` 로 설정하면, 물리적으로는 작은 배치를 돌리지만 수학적으로는 4배 큰 배치를 사용하는 효과를 얻을 수 있음. 배치 사이즈를 줄였을 때 발생하는 학습의 불안정성을 보상할 수 있음
        4. 4단계 그래디언트 체크포인트 : 순전파 중간 결과(활성화 값)을 저장하지 않고, 역전파 시 필요할 때 재계산 한다. 
    2. Adam은 왜 파라미터의 3~4배의 메모리를 쓰는가 
        1. Adam은 파라미터마다 Momentum과 Variance라는 두 가지 상태값을 저장한다. 따라서 모델 파라미터가 N개라면 옵티마이저 상태에서는 2N개, 혼합 정밀도 학습시 FP32 마스터 가중치에 1N개가 추가로 필요하다. 결과적으로 옵티마이저만으로 파라미터 크기의 3~4배 메모리가 필요하다. 
3. 프로파일링 결과에서 `get_train_batch`가 전체 시간의 60%를 차지한다면, 어떤 최적화를 우선 시도하시겠어요? 반대로 `training_step`이 90%라면요?
    1. `get_train_batch` 을 최적화 하기 위해서는 `DataLoader` 의 `num_worker` 을 늘리거나, 데이터 포맷 변경을 우선적으로 시도한다 
    2. `training_step` 이 90%를 차지한다는 것은 모델 연산 자체가 주 병목이라는 의미이다. 혼합 정밀도, `torch.compile`, 또는 모델 경량화를 시도한다. 
4. 스케일링 법칙의 "작은 실험 → 직선 외삽 → 필요 자원 추산" 흐름을 자신의 언어로 설명하고, 이것이 비즈니스적으로 어떤 가치를 주는지 설명해 보세요.
    1. 과거에는 성능을 올리기 위해서 무엇을 해야 할지를 직감에 의존했다. 하지만 현재는 수학적으로 예측 가능해졌다. 모델 성능(Loss)는 연산 예산(Compute), 데이터셋 크기, 파라미터 수라는 제 축에 따라 거듭제곱 법칙으로 향상된다. 로그-로그 스케일에서 직선으로 나타난다. 
    2. 파라미터수나 데이터의 크기를 점진적으로 늘리면서 3-5개의 작은 규모의 실험을 실행하고 각각의 최종 Loss를 기록한다. x축은 자원(Compute, data size, params), y축을 Loss로 두고 로그-로그 차트에 점을 찍어서 회귀 직선을 구한다. 이 직선을 연장하여 목표 Loss에 도달하기 위해서는 data size가 n배, GPU 시간이 k배 필요하다 등의 구체적인 숫자를 얻을 수 있다. 
5. 성능 저하 진단표(오버피팅/언더피팅/분포 변화)에서, 자신의 최근 프로젝트가 어떤 상황이었는지 분석하고 적절한 처방을 매칭해 보세요.
    1. 체육시설 안전점검 이미지 분류 프로젝트는 아직 수행하지 않은 아이디어 단계이므로, 이 프로젝트를 수행할 때 어떤 문제가 발생할 수 있는지 그리고 적절한 처방은 무엇일지를 고려해본다 
        1. 언더피팅 상황: 
            - **증상:** Train Loss도 안 떨어지고, Validation Loss도 높음. (모델이 균열과 그림자를 구분하지 못함)
            - **원인 분석:** 모델 크기가 너무 작거나(ResNet-18), 학습률이 안 맞거나, 이미지 전처리가 잘못됨.
            - **처방(해결책):** 모델 파라미터를 키우거나(ResNet-50으로 변경), 학습률 탐색(LR Finder) 수행.
        2. 오버피팅 상황: 
            - **증상:** Train Loss는 거의 0에 수렴해서 99% 정확도인데, Validation Loss는 높고 검증 정확도는 70%에 머뭄.
            - **원인 분석:** 훈련 데이터의 수가 부족해서 모델이 특징(균열 패턴)을 일반화하지 못하고 특정 체육관 벽면의 색깔이나 질감을 통째로 외워버림.
            - **처방(해결책):** Data Augmentation(회전, 밝기 조절, 크롭 등)을 강하게 적용하고, Dropout 비율을 높이거나 Early Stopping을 적용.
        3. 데이터 분포 변화 (Data Shift):
            - **증상:** Train/Val 모두 95% 이상 정확도가 나왔는데, 실제 체육관 현장에 앱을 배포해 보니 정확도가 50%로 뚝 떨어짐.
            - **원인 분석:** 훈련 데이터는 '낮에 고화질 카메라'로 찍은 사진들인데, 실제 현장에서는 '어두운 실내에서 저화질 스마트폰'으로 찍은 사진이 들어옴 (Domain Shift).
            - **처방(해결책):** 실제 스마트폰 환경에서 찍은 이미지를 추가 수집하여 재학습(Fine-tuning)하거나, 훈련 데이터에 가우시안 노이즈와 어둡게 만드는 Augmentation을 추가.

**✅ Chapter 15 체크포인트**

1. LLM 기반 시스템을 Accuracy만으로 평가할 수 없는 이유를 설명하고, 추가로 필요한 평가 차원을 5가지 나열할 수 있으신가요?
    1. 일반적인 프로그램은 정답이 존재하기 때문에 Accuracy(정확도)로 평가가 가능했다. 하지만 LLM 기반 시스팀(RAG, Agent, 챗봇 등)은 “이 답변이 정확한가?” 를 판단하는 여러가지 문항들이 존재하기 때문에 Accuracy, Precision, Recall, F1-Score 등의 단일 숫자 메트릭으로는 성능을 포착하기 어렵다. 
    2. 유창성(Fluency, 답변의 자연스러움), 사실성(Faithfulness, 환각 유무), 스타일(Tone, 적절한 톤), 의도 이해(Intent Understanding, 사용자 의도 파악), 안전성(Safety, 유해하거나 편향된 내용 포함 여부)
2. LLM-as-a-Judge의 장점과 주의할 한계(편향)를 각각 설명하고, 편향을 완화하는 방법을 하나 제안해 보세요.
    1. 장점 : 사람이 직접 판단하는 것과 비교하여 10-100배 빠르고 저렴하며, 사람의 평가와 상관관계가 0.7-0.9로 높음. 
    2. 한계점 : 평가 LLM 자체가 가지고 있는 편향(예: 길이 편향 - 긴 답변에 더 높은 점수를 부여, 위치 편향 - 먼저 제시된 답변을 선호) 존재 
    3. 예를 들어 길이 편향을 완화하기 위해서는 평가 프롬프트에 “답변을 평가할때 길이는 평가 기준에 넣지 않는다. 답변의 핵심만을 평가한다” 등의 지시를 포함한다. 위치 편향의 경우 평가 프롬프트에 “A와 B의 순서를 바꿔서 두 번 평가한 뒤 평균을 낸다”는 지시를 포함하는 방법을 사용한다. 
3. 입력 드리프트, 출력 드리프트, 성능 드리프트의 차이를 각각 한 문장으로 설명하고, 자신의 프로젝트에서 가장 가능성 높은 드리프트 유형은 무엇인지 분석해 보세요.
    1. 입력 드리프트 : 모델에 들어오는 입력 데이터의 통계적 분포가 시간이 지남에 따라 학습 시점과 달라지는 현상 
    2. 출력 드리프트 : 모델의 예측값 비율이나 분포가 실제 정답과 무관하게 변화하는 현상 
    3. 성능 드리프트 : 모델의 정확도, 정밀도 등의 성능 지표가 시간이 경과함에 따라 하락하는 현상 
    4. 앞서 언급한 “체육시설 안전점검 이미지 분류 프로젝트”을 수행할 때 발생 가능성이 가증 높은 드리프트 유형은 출력 드리프트라고 생각된다. 갑자기 “정상” 판정을 과도하게 예측한다거나, 예측 점수의 평균이 이동하는 등의 문제가 발생할 수 있다. 
4. "모델은 시간이 지나면 썩는다"는 말의 의미를 코로나19 같은 구체적 사례로 설명할 수 있으신가요? 이를 방지하기 위해 어떤 시스템이 필요한가요?
    - ML 모델은 전통 소프트웨어와 달리 코드 뿐만 아니라 입력되는 데이터도 모델에 큰 영향을 준다. 따라서 코로나 19와 같이 사람들의 생활 패턴이 판이하게 달라지는 경우, 이전의 데이터로 학습한 ML 모델에 전혀 다른 생황 패턴을 기반으로 하는 새로운 데이터가 입력 될 경우 코드가 바뀌지 않았지만 모델의 성능은 저하된다. 이를 방지하기 위해서는 모델을 자동으로 모니터링 할 수 있는 도구를 사용하여 모델 성능을 지속적으로 추적해야 한다.

    1. 가설: 본 프로젝트의 가장 큰 병목은 `get_train_batch` 단계의 **데이터 로딩 및 이미지 리사이징(스케일링) 과정**일 것이다. AI-Hub에서 수집한 원본 데이터는 해상도가 매우 큰 반면, ViT 모델은 224x224의 작은 입력값을 요구한다. 따라서 CPU가 고해상도 이미지를 디코딩하고 리사이징하는 속도가 느려, GPU가 연산을 대기하는 데이터 병목(I/O Bound) 현상이 크게 발생할 것으로 예상된다.
    2. 검증 계획 : 
        1. **시스템 지표 모니터링 (W&B 활용):** W&B의 시스템 대시보드를 통해 **GPU 사용률(Utilization)**을 확인한다. 만약 GPU 사용률이 90-100%를 꾸준히 유지하지 못하고 30-60% 구간에서 널뛰기한다면, GPU가 데이터를 기다리며 놀고 있다는 뜻이므로 가설이 입증된다.
        2. **PyTorch Profiler 활용:** `torch.profiler`를 켜고 몇 개의 배치를 돌려본 뒤 결과를 분석한다. 전체 학습 시간 중 `training_step`(모델 순전파/역전파 연산)이 차지하는 비율보다 `get_train_batch`(데이터로더가 이미지를 가져오는 시간)가 차지하는 비율이 압도적으로 높다면(예: 60% 이상) 가설이 정확히 입증된다.
        3. 가설이 사실로 확인된다면, 1) `DataLoader`의 `num_worker`를 늘려 다중 프로세싱으로 이미지를 불러오거나, 2) 학습 시작 전에 2만장의 이미지를 미리 224*224 해상도로 전부 리사이징하여 디스크에 새로 저장해주는 전처리 작업을 수행하여 병목을 해결한다. 
3. **1페이지 요약**: 완성된 워크시트를 1페이지로 요약해 보세요. 이것을 팀원이나 멘토에게 보여주고 피드백을 받을 수 있을 정도로 명확해야 합니다. 이것이 여러분의 Full Stack ML 프로젝트의 출발점이 됩니다.
