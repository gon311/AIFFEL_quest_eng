**✅ Chapter 0 체크포인트**

1. 모델 배포(FastAPI/Streamlit)와 Full Stack DL, 그리고 MLOps는 각각 어떤 범위를 담당하며, 왜 세 과정이 분리되어야 하는지 설명할 수 있으신가요?
    1. 모델 배포는 이미 완성된 모델이 있다는 전제 하에, 사용자에게 전달하는 인터페이스에 집중한다.
    2. Full Stack DL은 모델이 정말 완성되었는가에 대한 의심을 전제로 한다. 모델이 올바른 문제를 풀고 있는지, 데이터는 신뢰할 수 있는지, 실험 재현은 가능한지 등 모델의 생애 전체를 관리하는 엔지니어링 사고방식을 다룬다. 
    3. MLOps는 Full Stack DL의 사고방식을 실제 인프라로 구현한다. Docker로 환경을 격리하고, GCP 위에 파이프라인을 올리고, Airflow로 워크플로우를 자동화하고, CI/CD로 모델을 지속적으로 배포한다. 
2. "평평한 지구 ML"과 "둥근 지구 ML"의 차이를 동료에게 30초 안에 설명할 수 있으신가요? 데이터 플라이휠은 이 비유에서 어디에 해당하나요?
    1. 평평한 지구 ML은 문제를 정의하고, 데이터를 수집한후 모델을 학습시키고 평가를 하는 과정을 직선적으로 두고 모델이 좋은 성과를 냈다고 평가되면 프로젝트가 끝(done)되었다고 판단한다. 이에 반해 둥근 지구 ML은 모델을 배포한 후 사용자의 피드백과 새롭게 수집된 데이터들을 가지고 모니터닝하여 다시 기획에 반영하는 순환 구조를 가진다. 데이터 플라이휠은 개선된 모델이 더 많은 사용자를 끌어들일 수 있는 둥근 지구 ML에 해당한다. 
3. ML Powered Product와 MLOps의 지향점 차이를 구체적인 질문 하나씩으로 대비할 수 있으신가요?
    1. ML Powered Product :  사용자가 모델과 어떻게 상호작용을 하는가? 
    2. MLOps : 모델을 안정적으로 서빙하고 재학습시키는 파이프라인을 어떻게 구축할 것인가?

**✅ Chapter 1 체크포인트**

1. Software 1.0과 Software 2.0의 근본적인 차이는 무엇이며, 이 차이가 왜 전혀 다른 개발·테스트·운영 전략을 요구하는지 설명할 수 있으신가요?
    1. Software 1.0과 2.0의 근본적인 차이는 누가 코드를 작성하는가에 있다. 1.0은 프로그래머, 즉 사람이 명시적인 코드를 작성하고, 입력과 출력 사이의 관계를 사람이 직접 정의한다. 반면 2.0은 프로그래머가 데이터와 목적함수를 정의하면 모델은 스스로 입출력 관계를 학습한다. 즉 최적화 알고리즘이 데이터를 바탕으로 코드를 작성한다. 
    2. 즉 사람이 모든 것을 직접 정의하던 전통적인 소프트웨어와 달리, ML 제품은 데이터의 품질과 관리에 의해 동작이 결정되기때문에 근본적으로 다른 개발·테스트·운영 전략을 요구된다. 
2. CACE 현상(Changing Anything Changes Everything)이 전통적인 소프트웨어에서는 왜 덜 문제가 되고, ML 시스템에서는 왜 치명적인지 정리해 보셨나요?
    1. CACE 현상이란 모델의 한 파라미터나 데이터 입력 하나를 바꾸면 전체 시스템의 예측 결과가 예측 불가능하게 변하는 것을 의미한다. 
    2. 전통적인 소프트웨어는 사람이 입출력 관계를 정의하기 때문에 무엇이 입력되고 그 결과 무엇이 출력되는가가 명확하다. 하지만 ML 시스템에서는 입력되는 데이터의 분포가 끊임없이 변화한다. 따라서 데이터가 발생하는 외부 세계의 불안정성으로 인해 전체 시스템의 예측 결과가 예측 불가능해진다. 
3. "기술의 범용화(Commoditization)"가 ML 엔지니어의 역할을 어떻게 변화시키고 있는지 자신의 언어로 설명할 수 있으신가요?
    1. 기술의 범용화란, 특정 첨단 기술이 사회와 경제 전반에 널리 퍼져 모든 산업과 일상의 기본 인프라로 자리잡는 현상을 의미한다. 모델 학습의 범용화로 인하여 이제 ML 엔지니어는 모델을 만드는 사람에서 Foundation Model 위에서 제품을 설계하고, 자체 모델을 필요에 따라 Fine-tuning 할 수 있으며, 전체 시스템의 데이터 플라이휠을 관리하는 사람, 즉 모델을 제품에 통합하는 사람으로 확장되고 있다.

**✅ Chapter 2 체크포인트**

1. 현재 구상하고 계신 (혹은 관심 있는) ML 프로젝트를 실현 가능성 × 임팩트 매트릭스에 배치해 보셨나요? 어느 사분면에 위치하나요?
    1. 현재 구상하고 있는 “RAG를 활용한 AI 수영 코치 플랫폼”의 경우, 실현 가능성 측면에서는 High(RAG라는 효율적인 아키텍처와 양질의 데이터 확보 가능)이고, 비지니스적 임팩트는 Medium~High(기존의 오프라인 레슨과 단순 검색의 한계 해결)에 해당한다고 생각한다. 따라서 우상단이 Quick wins or High Value 사분면에 위치한다고 생각한다. 
2. Build vs. Buy vs. API 의사결정 트리에서, "API로 충분한가?"라는 질문에 답하기 위해 구체적으로 무엇을 확인해야 하는지 정리할 수 있으신가요?
    1. API로 충분하다는 의미는 해결하고자 하는 문제가 기존의 Foundation Model (OpenAI, Anthropic, Google 등)로 해결할 수 있는 수준임을 의미한다. 단, 비용과 지연시간, 데이터 보안을 고려해야 하며 이 부분에서 문제가 있다 판단되면 오픈 소스를 Fine-tuning 할지 여부를 고려한다. 
3. ML을 도입하기 전에 시도해야 할 4가지 대안을 나열하고, 각각이 더 적합한 상황을 예시와 함께 설명할 수 있으신가요?
    1. 규칙 기반 접근법 : 단순히 if-else 로직이나 정규표현식으로 80%의 성능을 낼 수 있다면 유지보수 측면에서 ML보다 훨씬 경제적이다. 예를 들어 단순한 계산기를 만든다고 가정한다면 굳이 ML을 도입하기 보다는 단순한 if-else, for문 등을 사용하여 만드는 것이 경제적이다. 
    2. 사람의 판단 : 의사 결정의 정확도가 극도로 중요한 영역의 경우, ML을 보조 도구로서 사용하는 것이 적절할 수 있다. 예를 들어 검사결과를 바탕으로 암을 판단하는 AI를 만든다고 가정하면, ML은 해당 결과가 암일 확률을 제시하고 최종적으로 암을 진단하는 것은 사람의 몫으로 두는 것이 보다 적절하다. 
    3. Foundation Model API 활용 : 현재, 많은 NLP 문제들은 기존의 Foundation model의 API를 호출하는 것 만으로도 충분한 성능을 낸다. 자체 모델 학습은 API로 해결할 수 없거나 또는 API를 사용했을 때 비용이 너무 많이 들거나, 또는 지연시간의 문제, 데이터 보안의 문제가 있을때 차선책으로 선택한다. 
    4. 전통적 통계 기법 : 태스트에 따라서 회귀 분석, 시계열 분석 등 해석 가능하고 검증된 통계 기법이 더 적합할 수도 있다. 예를 들어 계절별 사용자 추이 분석을 한다면, 계절이라고 하는 시계열의 특성상 같은 계정에는 비슷한 양상이 보일 가능성이 높다. 이런 경우 ML을 활용하는 것 보다 시계열 분석을 우선적으로 해보는 것이 보다 적합하다.

**✅ Chapter 3 체크포인트**

1. ML 프로젝트 라이프사이클 4단계를 순서대로 말할 수 있으신가요? 각 단계의 핵심 활동을 한 문장으로 요약해 보세요.
    1. 프로젝트 기획 및 설정 :  해결하고자 하는 비지니스 문제를 정의하고, ML 도입의 타당성과 목표 지표(Baseline)를 설정한다. 
    2. 데이터 수집 및 레이블링 : 모델을 학습시키기에 적합한 데이터를 수집하고, 라벨링을 통해 모델의 학습 방향을 설정한다.
    3. 모델 학습 및 디버깅 : 모델을 학습시키고, 디버깅을 통해 모델의 성능을 향상시킨다. 
    4. 배포 및 모니터링 : 모델을 배포하여 사용자들에게 제공하고, 사용자들의 피드백, 새로 입력되는 데이터 등을 모니터링하여 모델을 개선시킨다. 
2. "4단계 → 2단계 되돌아감"이 가장 흔한 이유는 무엇이며, 이를 미리 방지하기 위해 기획 단계에서 어떤 질문을 던져야 하는지 생각해 보셨나요?
    1. 정제된 데이터를 가지고 수행하는 오프라인 평가에서는 잘 돌아가지만, 실제 사용자 환경에서는 학습 데이터에 없던 입력이 들어오게 되면서 성능이 급감하게 된다. 이러한 실패 사례들을 수집하여 다시 레이블링 하고 학습 데이터의 추가하면서 모델의 성능을 끌어올릴 수 있다. 
    2. 다만 이를 최소화 하기 위해서는 기획 단계에서 실제로 모델이 배포되었을 때 어떤 입력이 들어오게 될지 시뮬레이션하고 이에 대한 대책을 강구하는 것이 요구된다. 
3. 데이터 플라이휠이 자연스럽게 형성되는 제품과 인위적으로 설계해야 하는 제품의 차이를 예시와 함께 설명할 수 있으신가요?
    1. 전자의 경우는 사용자가 제품을 사용하는 것 자체가 모델 학습에 유용한 데이터가 되는 경우를 의미한다. 예를 들어 넷플릭스에서 작품을 클릭하여 감상하거나, 좋아요를 누르는 자체가 모델 성능 향상을 위한 피드백이 된다. 후자의 경우, 수동으로 일정 기간의 데이터를 모아 재학습시키는 경우를 의미한다. 인프라, 인력, 비용 등을 고려하였을 때 수동으로 데이터를 수집하는 것도 좋은 초기 단계의 데이터 플라이휠이라 할 수 있다.

**✅ Chapter 4 체크포인트**

1. 세 가지 아키타입(Software 2.0, Human-in-the-loop, Autonomous) 각각에 해당하는 실제 서비스를 하나씩 떠올려 보실 수 있나요?
    1. Sofeware 2.0 : Google의 AI 기반 검색 서비스 실시 
    2. Human-in-the-loop : codex, antigravity, claude code 와 같은 AI 코딩 어시스턴트 
    3. Autonomous: 무인 운전 시스템 
2. 하나의 제품이 처음에는 Human-in-the-loop으로 시작하여 Autonomous로 진화하는 경로를 구체적으로 그려볼 수 있으신가요? 전환의 조건은 무엇일까요?
    1. Human-in-the-loop와 Autonomous의 차이는 인간 개입의 유무이다. 전자는 신뢰도가 낮은 케이스의 경우 인간에게 판단의 키를 넘긴다. 만약 Human-in-the-loop로 시작하여 데이터가 축적되고, 이를 바탕으로 충분히 신뢰도가 확보된 영역이 있다면 점진적으로 Autonomous로 진화할 수 있다. 
3. 자신이 만들고 싶은 ML 제품은 어떤 아키타입에 해당하며, 그에 따라 모델 정확도·실패 비용·데이터 플라이휠 전략이 어떻게 달라지는지 정리해 보셨나요?
    1. 내가 구상하는 AI 수영 코치 플랫폼은 Software 2.0 아키타입에 해당한다. 기존의 규칙 기반 시스템이 단순 키워드 검색 과정을 LLM과 RAG라는 신경망 구조로 대체하여 가치를 창출하기 때문이다. 또한, 코칭 조언을 최종적으로 취사선택하고 실행하는 것은 사람이므로 넓은 의미에서는 Human-in-the-loop 성격도 함께 가지고 있다. 
    2. 이에 따른 세가지 전략은 다음과 같다. 
        1. 모델 정확도 : 핵심은 완벽함 보다는 ‘기존 경험 대비 유용성’에 초점을 두는 것이다. 자율주행이나 의료 AI처럼 절대적인 정확도가 요구되는 도메인은 아니다. 사용자가 포털에서 키워드를 검색하고 수많은 글을 직접 읽으며 필터링해야 했던 기존 방식보다, 내 맥락을 이해하고 ‘유용한’ 조언을 해주는 것 만으로도 충분히 가치가 발생한다. RAG를 통해 신뢰할 수 있는 외부 문서에 기반한 답변을 생성하기때문에 기존 검색 서비스 대비 높은 만족도를 주는 수준의 정확도로도 상용화가 가능하다. 
        2. 실패 비용: 모델이 다소 엉뚱한 훈련법을 추천하더라도 재산성/생명상의 큰 타격은 없으므로 기본적인 실패비용은 낮다. 하지만 잘못된 자세 추천으로 인한 ‘부상 위험’은 통제해야 할 리스크이다. 따라서 RAG의 데이터 소스를 검증된 공식 자료 등으로 제한하고, 통증이나 의학적 조언을 구하는 질문에는 ‘전문의와 상담하세요’라고 답변하도록 가드레일을 설정하여 실패 비용을 최소화 할 수 있다. 
        3. 데이터 플라이휠 전략: 사용자가 입력하는 구체적인 고민들 자체가 매우 가치 있는 도메인 데이터(Long-tail Query)가 되어 자연스러운 플라이휠이 형성된다. 
            1. 사용자 질문 내용과 답변에 대한 명시적 피드백(좋아요/싫어요 버튼) 및 암시적 피드백(이어지는 후속 질문 등)을 수집
            2. 이 데이터를 분석하여 사용자들이 많이 찾지만 현재 우리 RAG DB에 부족한 ‘지식의 공백’을 찾아 문서 추가 
            3. 수집된 피드백을 바탕으로 사용자 의도에 맞게 문서를 더 잘 찾아오도록 검색 모델을 미세조정하여 쓰면 쓸수록 코칭의 질이 높아지는 선순한 구조 구축

    4. 업계 벤치마킹 : 현재 시장에는 AI 기술을 사용하여 코칭을 제공하는 서비스들이 존재한다. 다만 대부분은 고가의 장비를 바탕으로 수집된 데이터를 기반으로 연습방법을 제시하거나 연습 스케쥴을 구성하는 서비스를 제공하고 있다. 
3. "정확도에 9를 하나 더 추가하면 비용이 10배 증가한다"는 법칙이 자신의 프로젝트에 어떤 의미를 갖는지 생각해 보셨나요? 요구 정확도를 낮출 수 있는 제품 설계 방법은 없을까요?
    1. 수영 코칭 도메인은 자율주행처럼 절대적인 정확도가 요구되는 분야가 아니다. 따라서 90%의 정확도를 99%로 올리기 위해 값비싼 파인튜닝을 하거나 방대한 데이터를 수동으로 라벨링하여 막대한 비용을 쏟을 필요가 없다. 내가 추구하는 프로젝트의 목표는 ‘완벽한 정답’이 아니라, 기존의 포털 검색이나 룰 기반 앱 보다 훨씬 개인화되고 맥락에 맞는 조언을 제공하여 높은 만족도를 주는 것이므로, 막대한 비용을 들여 정확도의 ‘9’를 하나 더 늘리는 것은 ROI에 맞지 않다. 출처 제공을 통한 신뢰도 분산, 단일 정답이 아닌 여러 옵션 제공 등을 통해 사용자의 경험을 해치지 않으면서 시스템이 요구하는 정확도의 허들을 낮출 수 있을 것으로 예상된다. 
4. "당신은 구글이 아니다"라는 원칙에 비추어, 자신의 프로젝트에서 지금 당장 필요한 도구와 나중에 도입해도 되는 도구를 구분할 수 있으신가요?
    1. RAG 시스템의 기반이 되는 지식 스키마를 구축하고 이를 RAG와 연결시키는 것은 주피터 노트북 + 수동 파이프라인으로 충분하다. Docker, Airflow, Vertex AI 등의 도구들은 나중에 도입해도 무리가 없다.

**✅ Day 1 통합 체크포인트 — 오늘 배운 것을 하나로 꿰기**

1. **파이프라인 위치 인식**: "모델 배포 → Full Stack DL → MLOps"라는 3단계 학습 경로에서, 오늘 다룬 내용이 왜 모델 배포 직후이자 MLOps 직전에 위치해야 하는지를 자신의 언어로 설명할 수 있으신가요?
    1. 모델 배포는 모델이 완성되었다는 것을 가정한다. Full Stack DL은 그 생각에 의심을 가지는 것이다. 모델이 정말 ‘완성’되었는지, 사용한 데이터가 적합한지, 실험의 재현은 가능한지 등 모델의 생애 전체를 관리하는 엔지니어링 사고 방식이다. 그리고 MLOps는 이러한 사고를 실제 인프라로 구현하는 것이다. 
2. **종합 기획**: 관심 있는 ML 프로젝트 하나를 선택하여, 오늘 배운 프레임워크를 순서대로 적용해 보세요. (1) ML이 정말 필요한가? → (2) Build/Buy/API 중 무엇? → (3) 아키타입은? → (4) 실현 가능성 × 임팩트는? → (5) 비용의 3대 동인은? → (6) PoC 종료 조건은?
    1. 기존의 오프라인 레슨/단순 검색을 넘어서기 위해서는 LLM과 RAG를 이용한 ML 제품 필요하다.
    2. Foundation model API로 충분한 성능을 낼 수 있다. 다만 비용적인 측면은 데모를 통해 확인해야 한다.
    3. Software 2.0 (넓은 의미에서 Human-in-the-loop)
    4. 실현 가능성 High x 비지니스 임팩트 Medium~High 
    5. **API 토큰 비용**(LLM 호출 횟수에 비례. 사용자 늘어나면 증가함) / **데이터 인프라**(수영 코칭 문서를 벡터화하여 저장하고 검색하는 DB 유지 비용) / **데이터 큐레이션 인건비**(양질의 코칭 자료를 수집, 저작권 검토, RAG 포맷에 맞게 정제 하는데 드는 시간과 비용)
    6. 베타 테스터의 80% 이상이 유용함(좋아요)을 표시하고, 사용자 1인당 월평균 API 호출 비용이 예상 수익(구독료 등)의 30% 이하인 경우 **성공**. 반면 저작권 제약으로 인해 양질의 DB 목표치의 50% 이하를 달성하거나, 위험한 드릴을 추천하는 등의 치명적 환각 발생률이 5%를 초과할 경우 **실패**. 
3. **둥근 지구 설계**: 위에서 선택한 프로젝트의 데이터 플라이휠을 구체적으로 그려 보세요. 사용자의 어떤 행동이 데이터가 되고, 그 데이터가 어떻게 모델을 개선하며, 개선된 모델이 어떻게 더 많은 사용자를 끌어들이나요?
    1. 사용자가 입력하는 구체적인 수영 고민(프롬프트)과 그에 대한 반응(좋아요/싫어요)이 데이터가 된다. 이 중 '**싫어요'를 받은 질문들을 모아 분석하면 시스템의 지식 공백(Knowledge Gap)을 파악할 수 있다.** 해당 영역의 체육회 자료나 문헌을 새롭게 Vector DB에 추가(모델 개선)하면 답변의 퀄리티가 높아진다. 이렇게 날카로워진 코칭 성능은 수영 커뮤니티에 입소문을 타게 되고, 더 많은 사용자를 유입시켜 다시 더 많은 고민(프롬프트) 데이터가 쌓이는 플라이휠이 완성된다.
4. **실패 시나리오**: 위 프로젝트가 실패한다면 가장 가능성 높은 원인은 무엇일까요? 기술적 비실현성, 프로덕션 전환 실패, 조직 공감대 부족, 작은 문제 해결 중 어디에 해당하며, 이를 사전에 방지하기 위해 기획 단계에서 무엇을 할 수 있을까요?
    1. 지식 스키마 구성할때 **저작권**에 걸려서 많은 정보를 포함하지 못한다면 실패할 가능성이 높다. 이는 기획/프로토 타입 단계는 통과했으나 실제 서비스로 확장하지 못하는 ‘프로덕션 전환 실패’ 또는 ‘기술적 비실현성(Infeasibility, e.g., 합법적 데이터 확보 불가)에 해당한다. 
    2. 이를 사전에 방지하려면, 기획단계에서 (1) 저작권이 만료된 자료, (2) 공공 개방 데이터(대한체육회 등), (3) 출처 표기만으로 활용 가능한 논문 등으로 합법적 데이터셋의 바운더리를 먼저 규정해야 한다. 그리고 이 안전한 데이터만으로도 PoC가 성공할 수 있는지 먼저 검증해야 한다. 
5. **기술적 부채 예측**: 이 프로젝트가 성공적으로 배포된 후 6개월 뒤, 어떤 종류의 기술적 부채가 쌓여 있을 것으로 예상되시나요? CACE, 데이터 드리프트, 외부 세계의 불안정성(Instability) 중 어떤 것이 가장 위협적일까요?
    1. 외부 세계의 불안정성(가장 위험) : 자체 모델이 아닌 Foundation Model API를 사용하기 때문에, 만약 OpenAI가 모델을 업데이트함에 따라 우리 코드는 그대로인데 갑자기 코치 AI의 말투가 바뀌거나 대답 형식이 깨지는 등 ‘내가 통제할 수 없는 외부 요인’으로 시스템이 흔들리는 부채를 겪을 수 있다. 
    2. CACE 현상(데이터 측면): RAG 시스템에서 ‘문서를 자르는 단위(Chunk size)’를 살짝 변경하거나 ‘임베딩 모델’을 바꾸면, 기존에는 잘 답변하던 “자유형 발차기” 질문에 갑자기 엉뚱한 문서를 검색해오는 등 전체 시스템의 예측 결과가 요동칠 수 있다.
